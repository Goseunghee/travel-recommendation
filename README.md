# 🌍  Gemini + Google Places 여행 추천 프로그램

## 1. 프로젝트 소개

이 프로그램은 사용자가 입력한 여행 날짜를 기준으로 **Gemini API를 이용해 한국의 추천 여행지를 1곳 선정**하고, 추천된 지역을 **Google Places API를 이용해 검색하여 맛집 5곳을 찾는 CLI(Command Line Interface) 프로그램**이다.

프로그램은 사용자가 `YYYY-MM-DD` 형식으로 여행 날짜를 입력하면 날짜 형식을 검증한 후 Gemini API에 여행지 추천을 요청한다.

Gemini에서 추천한 여행지 정보를 JSON 형태로 받아 필요한 데이터를 추출하고, 추천된 지역을 Google Places API에 전달하여 해당 지역의 맛집 5곳을 검색한다.

최종 결과는 `results` 폴더에 JSON 파일과 Markdown 보고서로 저장한다.

또한 외부 API를 사용하는 과정에서 발생할 수 있는 오류에 대응하기 위해 오류 내용을 `errors` 배열에 기록하고, Gemini 모델 호출 실패 시 다른 모델로 자동 대체하는 fallback 기능과 429 오류 발생 시 재시도하는 기능을 구현하였다.

### 전체 프로그램 흐름

```text
사용자
  ↓
여행 날짜 입력
  ↓
날짜 형식 검증
  ↓
Gemini API
  ↓
추천 여행지 1곳 선정
  ↓
JSON 형태의 결과 생성
  ↓
추천 도시 추출
  ↓
Google Places API
  ↓
추천 지역 맛집 5곳 검색
  ↓
결과 정리
  ↓
JSON 파일 + Markdown 보고서 저장
```

## ✨2. 주요 기능

1. CLI 인자 `-date "YYYY-MM-DD"` 형태로 여행 날짜 입력
2. 입력한 여행 날짜의 형식 검증
3. `.env` 파일에서 API 키 및 모델 정보 로드
4. Gemini API를 이용한 한국 여행지 추천
5. 추천 여행지 정보를 JSON 형태로 구조화
6. JSON 결과에서 추천 도시 정보 추출
7. Google Places API를 이용한 해당 지역 맛집 5곳 검색
8. Gemini 결과와 Google Places 검색 결과를 연결
9. 결과를 `results` 폴더에 JSON 파일로 저장
10. 결과를 Markdown 보고서로 저장
11. API 오류 발생 시 `errors` 배열에 오류 내용 기록
12. Gemini 모델 호출 실패 시 다른 모델로 자동 대체
13. 429(Too Many Requests) 발생 시 재시도
14. 재시도 후에도 실패할 경우 fallback 수행
15. API 키를 코드에 직접 작성하지 않고 `.env`를 이용하여 관리

## 6. 🔐환경변수 및 API Key 설정

API Key를 Python 코드에 직접 작성하지 않고 `.env` 파일에 저장한다.

### `.env` 예시

```text
GEMINI_API_KEY=실제_Gemini_API_Key
GOOGLE_PLACES_API_KEY=실제_Google_Places_API_Key
```

Python에서는 `python-dotenv`를 이용하여 `.env` 파일을 읽는다.

```python
from dotenv import load_dotenv
import os

load_dotenv()

gemini_api_key = os.getenv("GEMINI_API_KEY")
google_places_api_key = os.getenv("GOOGLE_PLACES_API_KEY")
```

### API Key를 `.env`에 저장하는 이유

API Key를 코드에 직접 작성하면 GitHub에 소스 코드를 업로드했을 때 API Key가 함께 공개될 위험이 있다.

예를 들어 다음과 같이 작성하는 것은 좋지 않다.

```python
GEMINI_API_KEY = "실제_API_Key"
```

이 코드를 GitHub에 업로드하면 다른 사람이 API Key를 확인할 수 있다.

API Key가 노출되면 다른 사람이 해당 API Key를 사용하여 API를 호출할 수 있고, 예상하지 못한 API 사용량이 발생할 수 있다.

따라서 API Key는 `.env` 파일에 별도로 저장하고 Python에서는 환경변수로 불러온다.

또한 `.gitignore`에 `.env`를 추가하여 GitHub에 `.env` 파일이 업로드되지 않도록 한다.

```text
.env
```

### `.env`를 사용하는 이유

* API Key를 소스 코드와 분리할 수 있다.
* GitHub에 API Key가 공개되는 것을 방지할 수 있다.
* 개발 환경에 따라 다른 API Key를 사용할 수 있다.
* API Key를 변경해도 소스 코드를 수정할 필요가 없다.
* 인증 정보의 보안을 높일 수 있다.

# 8. 🔌REST API

## 8-1. REST API란?

REST API는 서로 다른 프로그램이나 서버가 HTTP를 이용하여 데이터를 주고받을 수 있도록 만든 인터페이스이다.

이번 프로젝트에서는 Python 프로그램이 Gemini API와 Google Places API에 요청을 보내고, 각 API에서 반환한 결과를 받아 다음 단계에서 사용한다.

프로그램은 API 서버와 직접 연결되어 모든 데이터를 처리하는 것이 아니라 필요한 정보를 API에 요청하고 API가 반환하는 데이터를 활용한다.

---

## 8-2. API Request와 Response

API 통신은 크게 **Request(요청)**와 **Response(응답)**으로 나눌 수 있다.

### Request

Request는 클라이언트가 서버에 보내는 요청이다.

API를 호출할 때 다음과 같은 정보가 사용될 수 있다.

* URL
* HTTP Method
* Header
* Query Parameter
* Request Body

이번 프로젝트에서는 Python 프로그램이 API를 호출하는 클라이언트 역할을 한다.

### Response

Response는 서버가 요청을 처리한 후 클라이언트에게 반환하는 결과이다.

일반적으로 다음과 같은 정보를 포함한다.

* HTTP Status Code
* Response Header
* Response Body
* JSON 데이터
* 오류 코드
* 오류 메시지

예를 들어 요청이 정상적으로 처리되면 `200 OK`와 함께 요청한 데이터를 받을 수 있다.

---

# 9. HTTP 메서드 GET과 POST

HTTP 메서드는 클라이언트가 서버에 어떤 작업을 요청하는지 나타낸다.

## 9-1. GET

GET은 주로 서버에서 데이터를 **조회하거나 가져올 때** 사용한다.

예를 들어 장소 검색 API에서 특정 지역의 맛집 정보를 가져오는 것과 같은 작업에 사용할 수 있다.

```text
GET 요청
  ↓
서버에서 데이터 조회
  ↓
검색 결과 반환
```

## 9-2. POST

POST는 서버에 데이터를 전달하거나 서버에서 특정 처리를 수행하도록 요청할 때 사용한다.

GET과 달리 Request Body에 데이터를 담아서 서버에 전달할 수 있다.

```text
POST 요청
  ↓
데이터 전달
  ↓
서버에서 처리
  ↓
결과 반환
```

간단하게 정리하면 다음과 같다.

| 메서드  | 주요 용도          |
| ---- | -------------- |
| GET  | 데이터 조회         |
| POST | 데이터 전달 및 처리 요청 |

단, 모든 API가 동일한 방식으로 동작하는 것은 아니다. 실제 API를 사용할 때는 해당 API의 공식 문서에서 어떤 HTTP 메서드를 사용하는지 확인해야 한다.

# 10. Gemini API를 이용한 여행지 추천

프로그램에서는 사용자가 입력한 여행 날짜를 기준으로 Gemini API에 여행지 추천을 요청한다.

Gemini는 입력된 여행 날짜를 바탕으로 한국의 여행지 중 한 곳을 추천하고, 해당 여행지와 관련된 정보를 생성한다.

프로그램에서 Gemini의 결과를 다음 단계에서 사용하기 위해 **JSON 형태로 구조화**한다.

---

## 10-1. LLM 결과를 JSON으로 사용하는 이유

Gemini가 일반적인 자연어 문장으로만 결과를 반환하면 프로그램에서 특정 정보를 추출하기 어려울 수 있다.

예를 들어 다음과 같은 결과가 있다고 가정한다.

```text
2026년 8월 여행지로 강릉을 추천합니다.
강릉은 바다 관광을 즐길 수 있고 여름철 여행지로 적합합니다.
```

사람이 읽기에는 문제가 없지만 Python 프로그램에서 정확하게 여행지 이름을 추출하기는 어렵다.

따라서 다음과 같이 일정한 JSON 구조를 사용한다.

```json
{
  "recommended_city": "강릉시",
  "weather": "덥고 습한 여름 날씨",
  "events": [
    "여름 축제"
  ],
  "reason": "바다 관광과 여름 행사를 즐기기 좋음"
}
```

이렇게 하면 Python에서 `recommended_city`라는 특정 값을 찾아서 사용할 수 있다.

---

## 10-2. JSON 결과를 Google Places API에 전달

Gemini의 결과에서 `recommended_city` 값을 추출한다.

예를 들어 Gemini가 다음과 같은 결과를 반환했다고 가정한다.

```json
{
  "recommended_city": "강릉시"
}
```

Python에서는 `"강릉시"`라는 값을 추출한 뒤 Google Places API의 검색어로 사용할 수 있다.

전체 과정은 다음과 같다.

```text
Gemini API
    ↓
JSON 응답
    ↓
recommended_city 추출
    ↓
"강릉시"
    ↓
Google Places API 검색
    ↓
강릉시 맛집 검색
    ↓
맛집 5곳 결과
```

즉, JSON은 단순히 결과를 저장하는 형식이 아니라 **한 API의 결과를 다음 API의 입력값으로 전달하기 위한 중간 데이터 구조**로 활용된다.

---

# 11. Google Places API를 이용한 맛집 검색

Gemini에서 추천한 도시를 Google Places API에 전달하여 해당 지역의 맛집을 검색한다.

예를 들어 추천 여행지가 `강릉시`라면 프로그램은 해당 지역을 기준으로 장소 검색을 수행한다.

검색 결과 중 필요한 정보를 정리하여 맛집 5곳을 최종 결과에 포함한다.

전체적인 API 연결 구조는 다음과 같다.

```text
사용자
  ↓
여행 날짜
  ↓
Gemini API
  ↓
추천 여행지
  ↓
JSON 구조화
  ↓
추천 도시 추출
  ↓
Google Places API
  ↓
맛집 검색
  ↓
맛집 5곳
```

# 12. 결과 저장

프로그램 실행이 완료되면 결과를 `results` 폴더에 저장한다.

### JSON 파일

JSON 파일에는 프로그램에서 처리한 여행지 정보와 맛집 검색 결과 등을 구조화된 형태로 저장한다.

JSON은 프로그램에서 다시 데이터를 읽거나 다른 프로그램과 데이터를 주고받을 때 활용하기 좋다.

### Markdown 파일

Markdown 파일에는 사용자가 확인하기 쉬운 형태로 여행 결과를 정리하여 저장한다.

따라서 JSON은 **데이터 처리와 저장에 적합한 형식**이고, Markdown은 **사람이 읽기 쉬운 보고서 형식**으로 활용한다.

# 13. 외부 API 오류 처리

외부 API를 사용할 때는 항상 정상적인 응답이 반환되는 것은 아니다.

API Key 문제, 권한 문제, 잘못된 요청, 요청 횟수 제한, 서버 오류, 네트워크 오류, JSON 파싱 오류 등 여러 가지 문제가 발생할 수 있다.

따라서 오류가 발생하면 단순히 프로그램을 다시 실행하기보다는 **HTTP 상태 코드와 실제 응답 내용을 확인하여 원인을 파악하는 것**이 중요하다.

---

## 13-1. 400 Bad Request

요청 자체가 잘못된 경우 발생한다.

### 원인

* 필수 파라미터 누락
* 잘못된 파라미터 이름
* 잘못된 데이터 형식
* 잘못된 요청 값
* API에서 요구하지 않는 형식 사용

### 대응

API 공식 문서를 확인하고 필수 파라미터와 데이터 형식이 올바른지 확인한다.

---

## 13-2. 401 Unauthorized

인증에 실패했을 때 발생한다.

### 원인

* API Key가 잘못됨
* API Key가 누락됨
* Client ID 또는 Client Secret 오류
* 인증 Header 오류
* 인증 정보가 유효하지 않음

### 대응

API Key가 정확한지 확인하고 `.env` 파일의 환경변수가 정상적으로 로드되는지 확인한다.

또한 API가 요구하는 인증 방식과 Header 형식이 정확한지 확인한다.

---

## 13-3. 403 Forbidden

인증은 되었지만 해당 기능을 사용할 권한이 없을 때 발생할 수 있다.

### 원인

* API 서비스가 활성화되지 않음
* 해당 API 사용 권한이 없음
* 프로젝트 설정 문제
* API 사용 제한

### 대응

API 관리 콘솔에서 해당 API가 활성화되어 있는지 확인하고 필요한 권한이 설정되어 있는지 확인한다.

```text
401 → 인증 문제
403 → 권한 문제
```

---

## 13-4. 404 Not Found

요청한 URL이나 리소스를 찾을 수 없을 때 발생한다.

### 원인

* API URL 오타
* 잘못된 endpoint
* 존재하지 않는 리소스 요청

### 대응

API 공식 문서와 코드의 URL을 비교하고 endpoint가 정확한지 확인한다.

---

## 13-5. 408 Request Timeout

서버가 요청을 처리하는 데 너무 오래 걸려 시간 제한이 발생한 경우이다.

### 대응

* 인터넷 연결 확인
* timeout 설정 확인
* 서버 상태 확인
* 필요한 경우 재시도

---

## 13-6. 429 Too Many Requests

짧은 시간에 너무 많은 요청을 보내거나 API 사용량 제한을 초과했을 때 발생한다.

이번 프로젝트에서는 429 오류가 발생하면 **재시도한 후에도 실패할 경우 fallback을 수행**하도록 구현하였다.

```text
API 요청
  ↓
429 발생
  ↓
재시도
  ↓
성공 → 계속 진행
  ↓
실패
  ↓
Fallback 수행
```

무작정 계속 요청하는 것이 아니라 일정 시간 기다린 후 다시 요청하는 것이 중요하다.

---

## 13-7. 500 Internal Server Error

서버 내부에서 문제가 발생한 경우이다.

클라이언트의 요청이 반드시 잘못되었다는 의미는 아니며 API 서버 자체의 일시적인 문제일 수도 있다.

### 대응

* 요청 내용 확인
* API 서버 상태 확인
* 잠시 후 재시도
* 오류 내용 기록

---

## 13-8. 502 Bad Gateway

중간 서버 또는 게이트웨이가 다른 서버로부터 정상적인 응답을 받지 못했을 때 발생할 수 있다.

### 대응

일시적인 서버 문제일 가능성이 있으므로 서버 상태를 확인하고 필요하면 재시도한다.

---

## 13-9. 503 Service Unavailable

서버가 일시적으로 요청을 처리할 수 없는 상태이다.

### 원인

* 서버 과부하
* 서버 점검
* 일시적인 서비스 장애

### 대응

잠시 기다린 후 다시 요청하거나 API 서버의 상태를 확인한다.

---

# 14. HTTP 상태 코드 외의 오류

## 14-1. 네트워크 오류

HTTP 응답 자체를 받기 전에 네트워크 연결 문제가 발생할 수 있다.

### 예시

* 인터넷 연결 끊김
* DNS 오류
* 서버 연결 실패
* Connection Timeout
* SSL/TLS 연결 문제

### 대응

네트워크 연결 상태와 API URL을 확인하고 Python에서 timeout과 예외 처리를 적용한다.

---

## 14-2. JSON 파싱 오류

API가 반환한 데이터가 프로그램에서 예상한 JSON 형식과 다른 경우 발생한다.

예를 들어 프로그램이 다음과 같은 응답을 예상한다고 가정한다.

```json
{
  "recommended_city": "강릉시"
}
```

하지만 실제 응답이 다음과 같이 일반적인 텍스트라면 JSON으로 처리할 수 없다.

```text
강릉을 추천합니다.
```

### 대응

* 실제 API 응답 확인
* JSON 구조 확인
* 필요한 필드 존재 여부 확인
* JSON 파싱 과정에서 예외 처리

---

## 14-3. API Key 누락 오류

`.env` 파일에 API Key가 존재하더라도 환경변수 이름이 잘못되었거나 `.env` 파일이 제대로 로드되지 않으면 API Key를 가져오지 못할 수 있다.

예를 들어 코드에서는:

```text
GEMINI_API_KEY
```

를 사용하는데 `.env`에서 다른 이름으로 저장했다면 정상적으로 불러올 수 없다.

따라서 코드와 `.env`의 환경변수 이름이 정확하게 일치해야 한다.

---

## 14-4. API 응답 구조 오류

API 응답에 프로그램이 예상한 필드가 없을 수도 있다.

예를 들어 프로그램에서 `recommended_city`가 항상 존재한다고 가정했지만 실제 응답에 해당 필드가 없다면 오류가 발생할 수 있다.

### 대응

필드가 존재하는지 확인한 후 사용하고, 예상하지 못한 응답이 들어왔을 때도 프로그램이 종료되지 않도록 예외 처리를 한다.

---

# 15. 오류 발생 시 대응 원칙

외부 API 오류가 발생하면 다음 순서로 확인한다.

```text
1. 오류 발생
      ↓
2. HTTP 상태 코드 확인
      ↓
3. 실제 응답 내용 확인
      ↓
4. 요청 URL 확인
      ↓
5. 요청 파라미터 확인
      ↓
6. API Key 및 인증 정보 확인
      ↓
7. API 권한 및 활성화 상태 확인
      ↓
8. API 사용량 및 쿼터 확인
      ↓
9. JSON 응답 구조 확인
      ↓
10. 필요하면 재시도 또는 fallback
```

오류의 종류에 따라 대응 방법도 달라진다.

| 오류         | 의미        | 주요 확인 사항           |
| ---------- | --------- | ------------------ |
| 400        | 잘못된 요청    | 파라미터, 데이터 형식       |
| 401        | 인증 실패     | API Key, 인증 Header |
| 403        | 권한 없음     | API 활성화, 권한        |
| 404        | 리소스 없음    | URL, endpoint      |
| 408        | 요청 시간 초과  | timeout, 네트워크      |
| 429        | 요청 제한     | 쿼터, 요청 횟수          |
| 500        | 서버 내부 오류  | 서버 상태, 재시도         |
| 502        | 게이트웨이 오류  | 서버 상태, 재시도         |
| 503        | 서비스 이용 불가 | 서버 상태, 재시도         |
| 네트워크 오류    | 연결 문제     | 인터넷, URL, timeout  |
| JSON 오류    | 데이터 형식 문제 | 응답 구조, 파싱          |
| API Key 누락 | 인증 정보 없음  | `.env`, 환경변수       |

이번 프로젝트에서는 오류 발생 시 `errors` 배열에 기록하도록 하였으며, Gemini 모델 호출에 실패하면 다른 모델로 자동 대체하도록 구성하였다.

또한 429 오류가 발생할 경우 재시도하고, 재시도 후에도 실패하면 fallback을 수행하도록 구현하였다.

---

# 16. Gemini 모델 Fallback

외부 LLM API를 사용할 때 특정 모델 호출이 실패할 가능성이 있기 때문에 하나의 모델만 사용하는 것보다 다른 모델을 사용할 수 있는 fallback 구조를 구성할 수 있다.

이번 프로젝트에서는 Gemini 모델 호출에 실패했을 경우 다른 모델로 자동 대체하는 기능을 구현하였다.

```text
기본 Gemini 모델
       ↓
    호출 실패
       ↓
다른 Gemini 모델
       ↓
    호출 성공
       ↓
    프로그램 계속 실행
```

이를 통해 특정 모델의 일시적인 오류가 발생하더라도 프로그램 전체가 바로 종료되는 것을 방지할 수 있다.

---

# 17. 429 오류 재시도 및 Fallback

429 오류는 API 사용량이나 요청 속도 제한과 관련된 오류이다.

이번 프로젝트에서는 429 오류가 발생했을 때 바로 프로그램을 종료하지 않고 재시도하도록 구성하였다.

```text
API 요청
  ↓
429 오류
  ↓
재시도
  ↓
성공?
 ├─ YES → 정상적으로 다음 단계 진행
 │
 └─ NO
      ↓
    Fallback
      ↓
다른 모델 또는 대체 처리
```

이와 같은 방식으로 일시적인 API 제한에 대응할 수 있다.

# 19. 학습 목표 정리

이번 과제를 통해 다음과 같은 내용을 학습하였다.

### REST API

REST API는 프로그램과 서버가 HTTP를 이용하여 데이터를 주고받는 방식이다.

API 요청에는 URL, HTTP 메서드, Header, Parameter 등의 정보가 포함될 수 있으며, 서버는 HTTP 상태 코드와 JSON 등의 데이터로 응답한다.

### GET과 POST

GET은 주로 데이터를 조회할 때 사용하고, POST는 데이터를 서버에 전달하거나 특정 처리를 요청할 때 사용한다.

단, 실제 API마다 사용하는 메서드가 다를 수 있으므로 API 공식 문서를 확인해야 한다.

### LLM 결과의 JSON 구조화

LLM은 자연어를 생성하기 때문에 결과가 일정한 형식이 아닐 수 있다.

따라서 JSON 형태로 결과를 구조화하면 프로그램에서 필요한 값을 쉽게 추출할 수 있다.

이번 프로젝트에서는 Gemini의 추천 결과에서 `recommended_city`를 추출하고 이를 Google Places API의 검색에 사용하였다.

### 외부 API 오류 처리

외부 API에서는 400, 401, 403, 404, 408, 429, 500, 502, 503 등의 HTTP 오류가 발생할 수 있다.

또한 네트워크 오류, API Key 누락, JSON 파싱 오류, API 응답 구조 오류 등이 발생할 수 있다.

오류가 발생하면 HTTP 상태 코드와 실제 응답 내용을 확인한 뒤 인증 정보, 권한, 요청 형식, URL, 쿼터, 네트워크 상태 및 JSON 구조 등을 순서대로 확인해야 한다.

### API Key 보안

API Key를 코드에 직접 작성하면 GitHub 등에 공개될 위험이 있기 때문에 `.env` 파일과 환경변수를 사용하여 관리한다.

또한 `.gitignore`에 `.env`를 등록하여 API Key가 포함된 파일이 Git 저장소에 올라가지 않도록 해야 한다.

# 20. 최종 정리

이번 프로젝트는 단순히 Gemini API를 호출하여 여행지를 추천받는 프로그램이 아니라, **LLM과 외부 장소 검색 API를 연결하여 하나의 결과를 만들어내는 API 연동 프로그램**이다.

전체적인 구조는 다음과 같다.

```text
여행 날짜 입력
      ↓
Gemini API
      ↓
여행지 추천
      ↓
JSON 구조화
      ↓
추천 도시 추출
      ↓
Google Places API
      ↓
맛집 5곳 검색
      ↓
결과 JSON 저장
      ↓
Markdown 여행 보고서 저장
```

이 과정에서 REST API의 요청과 응답 구조, GET과 POST의 차이, LLM 결과의 JSON 구조화, API 간 데이터 전달, 외부 API 오류 처리, 모델 fallback, 429 재시도, API Key 보안 관리 등을 학습하였다.

특히 하나의 API에서 얻은 결과를 JSON으로 구조화한 후 **다른 API의 입력으로 연결할 수 있다는 점**을 통해 여러 외부 서비스를 하나의 프로그램에서 연동하는 방법을 이해할 수 있었다.
